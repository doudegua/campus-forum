## 0. 先说结论：这不是新知识

抢课听起来是个大功能，但它其实是**三样你已经写过的东西的组合**：

| 抢课要做的事 | 你在哪写过同一件事 |
|---|---|
| 原子扣减库存，不能超卖 | `FlowLimitFilter` 的 `COUNT_SCRIPT`（Lua 原子性） |
| 一个人只能抢一次 | `TopicLikeServiceImpl.insertIgnore`（唯一索引幂等） |
| 计数必须原子，不能读-改-写 | 评论数/点赞数的 `SET n = n + 1` |
| 扣了不能白扣（失败要还回去） | 点赞"插入 0 行就不加计数"的那个判断 |

**所以你不需要从零理解，只需要理解"这三样怎么拼"。**

难的只有一个新东西：**为什么中间要插一个 MQ。**

## 3. 三个填空，按这个顺序写

### ① `CourseSelectionMapper.insertIgnore` —— 最简单，先写这个

**做什么**：一条 `INSERT IGNORE`，照抄 `TopicLikeMapper.insertIgnore`。

**判断依据是返回值**：

```
1 → 这次是第一次处理，允许给 db_course.selected_count +1
0 → 重复投递或早就抢到了，确认掉消息，绝不能再 +1
```

**为什么必须先写它**：因为消费端的整个分岔都挂在这个返回值上。这段写对了，后面两段才有意义。

**怎么验**：手工往队列里连发两条同样的消息，看 `db_course_selection` 是不是只有一行、`selected_count` 是不是只 +1。

---

### ② `CourseMapper.incrementSelectedIfAvailable` —— 第二写

**做什么**：一条带条件的 UPDATE。

```sql
UPDATE db_course SET selected_count = selected_count + 1
WHERE id = ? AND selected_count < capacity
```

**为什么必须是"一条语句"**：它把"判断还有没有名额"和"把名额用掉"压进同一个原子操作。写成"先 selectById 看余量，再 update"，中间就是一个窗口——**这个窗口你在点赞那里已经被咬过一次**（`AGENT.md` 第六节记着）。

**返回值 0 不是异常**，是"Redis 和 DB 的账对不上"的信号。这句话是面试点。

**为什么不用乐观锁版本号 / `FOR UPDATE`**：注释里写了，但建议你自己先想 30 秒——所有抢同一门课的人都在改同一行，版本号 CAS 会集体失败集体重试。

---

### ③ `CourseServiceImpl` 的 Lua + `select()` + `result()` —— 最后写，也是主体

**Lua 脚本骨架里已经给了完整代码**（`SELECT_SCRIPT` 的注释里），你的任务是**看懂它为什么这么写**，而不是抄：

```
-2  未预热（course:stock 键不存在）
-1  这个人已经抢过
 0  卖完了
>=0 扣完之后的剩余
```

**三个必须自己想明白的点**：

1. **为什么不能用 `DECR` 再判断返回值？** 因为 DECR 会先把库存扣成负数，你还得 INCR 还回去；中间那个负数在并发下会被别的请求读到。而且 DECR 单独用挡不住"同一个人重复扣两次"。
2. **为什么去重（SADD）要和扣减放在同一个脚本里？** 拆开就是 TOCTOU——两个请求都通过了去重检查，然后各扣一次。
3. **`select()` 为什么不能加 `@Transactional`？** 因为它只碰 Redis 和 MQ，没有 DB 写。加了会让人误以为"扣库存能跟着事务回滚"——**不能**。

**发 MQ 失败必须补偿**（INCR + SREM）：不补偿就是"这个名额永远少一个，而且用户不知道"。这是少卖，不是超卖，但同样是账不平。

**`result()` 的高频陷阱**：它是前端轮询接口，必须一次 Redis GET，不能查库。而且**不能返回 404 表示"还没结果"**——前端分不清"没抢到"和"还在排队"。

## 4. 四个陷阱（现在就知道，省你几小时）

| 陷阱 | 后果 |
|---|---|
| **消费端现在是"确认并丢弃"** | `CourseSelectListener` 现在收到消息只打日志然后 ack。**在①②写完之前，绝对不要接上生产端**，否则抢课请求会"成功"但永远不落库 |
| **补偿必须在事务之后** | 补偿（INCR+SREM）写在 `@Transactional` 方法里的话，事务回滚后补偿照样执行，库存就白多回来了 |
| **业务失败不能重试** | "名额已满""重复抢"重试一万次还是失败。只有 DB 临时故障才值得重试 |
| **`INSERT IGNORE` 有前提** | 它把所有可恢复错误降级成警告。这两列都是 int 所以安全；换成 varchar 就得改 `ON DUPLICATE KEY UPDATE` |

## 5. 自测：能答上来才算过了

不看代码，口头回答：

1. 三段式里，哪一段是可以省的？省了会怎样？
2. `course:stock:{id}` 键不存在时，为什么不能当成 0？
3. 消费者收到重复消息，`insertIgnore` 返回 0，接下来该做什么、绝不该做什么？
4. `selected_count` 更新返回 0 行，说明什么？要不要重试？
5. 发 MQ 抛异常时，已经扣掉的库存怎么办？
6. 为什么 `select()` 不加事务？
7. `result()` 为什么不能用 `SELECT` 查 `db_course_selection` 来判断结果？

**第 3、4、5 题答不出来，就说明消费端还没懂。** 这三题是面试官最可能问的，因为它们是"你真的处理过失败"和"照着教程抄的"的分界线。

## 6. 什么时候能写进简历

**现在不能。** 代码是骨架，三段核心是空的。

**能写的最低标准**：上面 7 题全答得上来，**并且**你自己能压测出至少一个数字（比如"1000 名额 5000 并发，`db_course_selection` 恰好 1000 行，零超卖"）。

那个数字是这条 bullet 唯一的价值来源——它证明的是"并发下我的账是平的"，不是"我用了 Redis 和 MQ"。

---

## 7. 一句话总结这个模块的设计

> **拿 Redis 当闸门（挡住绝大多数请求），拿 MQ 当缓冲（让 DB 只处理真的抢到的人），拿条件 UPDATE 当最后一道防线（Redis 算错了也不超卖）。**

三层各挡一层，任何一层单独都不成立。这就是"三段式"的意思。
